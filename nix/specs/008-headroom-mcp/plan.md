# Implementation Plan: Full Headroom Integration

**Feature Directory**: `008-headroom-mcp` | **Date**: 2026-09-08 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/008-headroom-mcp/spec.md`

## Summary

Build Headroom v0.36.0 with its official `[all]` feature closure, preserving upstream Rust ML
features and privately pinning Python dependencies that do not match the locked package set.
Package default tokenizer and model assets as fixed-output derivations and expose them through an
offline runtime environment. Register Headroom once in the central MCP registry and add a separate
opt-in `codex-headroom` launcher that runs a loopback proxy without mutating Codex or project files.
Antigravity CLI receives the full MCP integration but retains direct provider routing.

## Technical Context

**Configuration language**: Nix, with small shell/Python test helpers generated by Nix

**Flake architecture**: `flake-parts`, NixOS, Home Manager

**Affected hosts**: both (`nixos`, `nixos-wsl`)

**Affected layers**: flake inputs and packages, pinned model assets, shared Home Manager modules,
central MCP registry, generated client configurations, package/configuration/VM tests, system memory

**Inputs/packages/options**: `headroom-src` v0.36.0; `packages.headroom`; private Python package-set
pins for version/security gaps; fixed-revision Hugging Face/OCR/tokenizer assets;
`programs.mcp.servers.headroom`; new `internal.headroom.enable`; existing MCP client integrations

**State or migration impact**: no state-version migration; Headroom may create user-scoped caches,
memory, statistics, and logs under its runtime directories and project-scoped state when the user
explicitly invokes those workflows; rollback does not delete them

**Security impact**: opt-in proxy listens on `127.0.0.1` only and handles live Codex provider
authentication/content in process; no credentials are declared, persisted, logged, or globally
exported; external telemetry and remote model inference are disabled by default

**Rollback**: activate the previous generation or revert the feature; remove disposable
`~/.headroom` or project `.headroom` state manually only if desired

**Constraints**: multi-gigabyte CPU ML closure; no CUDA requirement; no runtime package/model
downloads; no Headroom registrar/install commands; preserve upstream ML behavior; ordinary `codex`
and `agy` commands remain unchanged; Antigravity provider proxying is unsupported

## Current and Target Design

### Current

`modules/home/mcp.nix` owns one registry projected by Codex, Antigravity CLI, and OpenCode.
`modules/home/codex.nix` preserves user-owned settings while replacing only centrally managed MCP
tables. There is no Headroom package, model asset, proxy launcher, local listener, or Headroom state
boundary.

### Target

The flake exposes a full Headroom package built from its locked source and Cargo lock. A private
Python package set supplies upstream-compatible versions without changing the global nixpkgs
package set. Fixed model snapshots and tokenizer files are assembled into read-only caches, and the
Headroom wrapper forces offline model/binary behavior. A focused Home Manager module installs
Headroom and `codex-headroom`; the latter owns an ephemeral loopback proxy and passes a process-local
Codex configuration override. The existing MCP registry launches `headroom mcp serve` from the
store. No Headroom install/reconcile command edits managed configuration.

### Decision Rationale

The upstream complete bundle is the requested supported boundary; separately installable provider
frameworks and external databases are not part of `[all]`. Runtime `uv`, `pip`, model downloads,
and mutable cache seeding violate reproducible ownership. An always-on proxy needlessly widens the
socket and credential boundary. Upstream `headroom wrap codex` still executes registrar cleanup,
so a repository-owned ephemeral launcher is safer. Direct Antigravity proxying is excluded because
its Cloud Code protocol remains unreliable through Headroom.

## Delivery and Recovery

1. Pin source, compatible Python packages, and immutable model/tokenizer assets; build Headroom in
   isolation before referencing it from either host.
2. Add package installation and the opt-in launcher, then register MCP centrally and add
   evaluation/runtime assertions before activating.
3. Run the verification ladder from formatting through both VM targets.
4. Apply with `nh os switch .`; use normal `codex`/`agy` for direct traffic and `codex-headroom`
   only for explicit proxy sessions.
5. Roll back to the previous generation or revert and switch; retained Headroom state is harmless
   and manually removable.
