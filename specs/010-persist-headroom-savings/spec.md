# Feature Specification: Persist Headroom Savings

**Feature Directory**: `010-persist-headroom-savings`

**Created**: 2026-09-09

**Status**: Draft

**Input**: "Record Headroom savings when Codex is launched through the Headroom wrapper."

Before completing this specification, read `.specify/memory/constitution.md` and
`.specify/memory/current-system.md`. Describe desired behavior, not implementation.

## Intent and Scope _(mandatory)_

### Problem

The opt-in Codex Headroom wrapper currently deletes its complete session workspace when
Codex exits. This also deletes Headroom's savings history, so the configured user cannot
review how many input tokens or how much estimated cost the wrapper saved.

### Desired Outcome

Savings generated by wrapped Codex sessions remain available after those sessions exit and
accumulate in the same user-scoped history used by the configured Headroom MCP integration.
Temporary proxy logs, memory, caches, and configuration remain isolated to each wrapper
session and are still removed on exit.

### Out of Scope

- Persisting proxy logs, memory databases, model caches, or temporary configuration.
- Enabling external telemetry or subscription tracking.
- Changing normal Codex routing or automatically wrapping every Codex invocation.
- Recovering savings information deleted by earlier wrapper sessions.

## Affected Targets _(mandatory)_

| Target or layer                  | Affected? | Expected observable change                                      |
| -------------------------------- | --------- | --------------------------------------------------------------- |
| `nixos` host                     | Yes       | Wrapped Codex savings persist in the configured user's history. |
| `nixos-wsl` host                 | Yes       | Wrapped Codex savings persist in the configured user's history. |
| Shared NixOS modules             | No        | N/A                                                             |
| Shared Home Manager modules      | Yes       | The wrapper retains only the savings ledger across sessions.    |
| Developer shell or agent tooling | Yes       | `headroom savings` reports savings from wrapped Codex sessions. |
| CI, caching, or verification     | Yes       | Headroom launcher assertions cover the state split.             |

## User Scenarios & Testing _(mandatory)_

Treat the operator, configured user, and downstream project as the relevant users. Each
story represents an independently verifiable configuration outcome.

### User Story 1 - Review Wrapped Codex Savings (Priority: P1)

After using the opt-in wrapper, the configured user can inspect cumulative Headroom savings
without needing to keep the original Codex session running.

**Why this priority**: Retained and inspectable savings are the requested outcome.

**Independent Test**: Evaluate the generated launcher and verify that proxy savings events
are directed to the persistent user-scoped Headroom data area rather than the disposable
session workspace.

**Acceptance Scenarios**:

1. **Given** a wrapped Codex session that produces a compression event, **When** the session
   exits normally, **Then** the event remains in the configured user's Headroom savings
   history and is included in the savings report.
2. **Given** multiple wrapped Codex sessions, **When** each produces compression savings,
   **Then** their events accumulate in one user-scoped savings history.

### User Story 2 - Preserve Session Isolation (Priority: P2)

The configured user continues to receive an isolated proxy and memory workspace for each
wrapped Codex session.

**Why this priority**: Savings retention must not unintentionally retain prompts, memory,
logs, caches, or configuration that the wrapper currently treats as temporary.

**Independent Test**: Verify that the launcher still creates and cleans a temporary
workspace while directing only the savings history outside it.

**Acceptance Scenarios**:

1. **Given** a wrapped Codex session, **When** it exits, **Then** its proxy process stops and
   temporary workspace is removed while the savings ledger is preserved.
2. **Given** the Headroom proxy starts through the wrapper, **When** its options are inspected,
   **Then** external telemetry and subscription tracking remain disabled.

### Edge Cases

- The persistent Headroom data directory does not exist before the first savings event.
- The wrapper exits because Codex fails or receives an interrupt.
- The Headroom MCP server and wrapped Codex proxy append savings concurrently.
- No compression occurs during a wrapped session, so no savings event is written.

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: The wrapper MUST retain savings events after a wrapped Codex session exits.
- **FR-002**: Wrapped-session savings MUST accumulate in the configured user's existing
  persistent Headroom savings history.
- **FR-003**: The retained history MUST remain readable through Headroom's savings-reporting
  command.
- **FR-004**: The wrapper MUST continue removing its temporary proxy, memory, log, cache, and
  configuration state when the session exits.
- **FR-005**: An absent persistent Headroom data directory MUST be handled automatically when
  the first savings event is recorded.

### Invariants

- **INV-001**: Normal Codex invocations MUST continue routing directly to the provider.
- **INV-002**: The opt-in proxy MUST remain bound to loopback and scoped to its child Codex
  process.
- **INV-003**: Headroom external telemetry and subscription tracking MUST remain disabled.
- **INV-004**: No state-version, credential, trust, cache, or unfree-package policy changes are
  permitted.

### Security and State

- **SEC-001**: The persistent ledger MUST remain user-scoped and MUST contain only Headroom's
  savings-event accounting data; no new external reporting is enabled.
- **STATE-001**: Savings events are retained for Headroom's supported reporting window. No
  migration of previously deleted events is possible or required, and rollback may leave the
  accumulated ledger as harmless user-owned state.

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: A savings event from a completed wrapped session is still reported afterward.
- **SC-002**: Savings from at least two wrapped sessions are aggregated into one history.
- **SC-003**: Verification proves that exactly the savings ledger is persistent while all
  other wrapper session state retains its prior cleanup behavior.
- **SC-004**: Formatting and the relevant Headroom configuration tests pass on both supported
  host evaluations.

## Current-System Impact _(mandatory)_

- **Claims to update**: Update "Home Manager and Agent Tooling" to distinguish the persistent
  shared savings ledger from the wrapper's otherwise temporary Headroom state.
- **Limitations resolved or introduced**: Wrapped-session savings are no longer discarded;
  historical savings deleted before this change remain unrecoverable.

## Assumptions

- Headroom's append-only, file-locked savings ledger safely supports concurrent MCP and proxy
  writers.
- The existing user-scoped XDG Headroom data directory is the canonical shared location for
  persistent savings history.
- Headroom's built-in retention and aggregation behavior remains authoritative.
